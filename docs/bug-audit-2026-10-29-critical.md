# 重大バグの追加調査と修正（2026-10-29）

基点は PR #57 までを取り込んだ main `1c1a9367fd94a5be23facd53f9def6dad58d2267`。権限昇格、保存データの破損、サービス停止につながる経路を優先した。以下は本番アカウント・本番ファイルを操作せず、使い捨て環境と基点のソースで再現した問題。

## 修正した問題

| 問題 | 影響と条件 | 修正 |
|---|---|---|
| 運営者間の認証情報漏えい・再設定（重大） | 一般運営者へのプレイヤー一覧・詳細・変更応答にも開発者や他の運営者の引き継ぎコードが含まれた。パスワード・コードの再設定にも対象アカウントの権限検査がなく、開発者アカウントへの成り代わりが可能だった | 共通の対象者検査を追加。ほかの運営者の認証情報を扱えるのは開発者のみ。本人と通常プレイヤーへの対応は維持。一覧だけでなく、プレイヤー行を返す全経路でコードを非公開にし、画面の再設定ボタンも合わせた |
| 非同期確認中の運営権付与が反映されない（高） | パスワードのハッシュ化中に対象が運営者になっても、先に始めた一般運営者のリセットが成立した。開発者コードの検証待ちに運営者となった対象も、そのまま削除できた | ハッシュ・コード検証の後、対象の現在の情報と保護条件を読み直す。拒否時は認証情報・削除状態・セッションを変更しない |
| 保存完了・削除後の遅延アップロード（高） | raw本文を読む前のファイル状態しか検査せず、別の送信が保存を完了した後でも遅い送信がDBの実データを上書きできた。削除後には孤立チャンクが再作成された。R2でも先に開始して遅く確定した書込みが、完成ファイルのチャンクを置き換えた | 保存直前にファイル・認証・完了状態を再確認。R2のチャンクは条件付き作成にして上書きを禁止。同じ内容の再送は受け付け、異なる内容は409。DBからR2への移動も同じ保護と条件付き削除を使う |

| Content-Lengthに依存した受信上限（高） | 通常APIのWorker入口がヘッダーだけで上限を検査し、その後は本文全量を読み込んだ。長さ不明・偽の短い長さのストリームが上限を超えてメモリを消費できた | 実際の受信バイト数を数え、上限を超えた時点で読込を中止して413。通常APIの9MiB、JSONチャンクの23MiBという既存上限は維持 |

## データと通常操作の互換性

- DBに `vault_files.storage_generation` を追加するだけの移行。既存ファイルは、過去の再開回数にかかわらず世代0とし、従来の `vault/<id>/<n>` を維持する。既存のチャンク・完了日時・ハッシュ・再開回数を変更しない。
- 更新後に再開したファイルだけ `vault/<id>/g<世代>/<n>` を使う。raw送信とJSON送信は同じチャンクを参照し、同じ内容の再送は冪等。クライアントの更新やファイルの再アップロードを要求しない。
- R2送信は引き続きWorkerからストリーミングし、ゲームのDurable Objectに大容量本文を通さない。チャンクごとの新しいDB書込みや常駐タイマーは追加しない。
- 旧スナップショットの世代省略は世代0として扱う。再開後の世代のスナップショットも、元ファイル削除後に復旧検証できる。
- コイン、価格、ガチャ確率、スロット配当、VIP、プレイヤー向け操作は変更しない。通常プレイヤーへの運営のパスワード・コード再設定、開発者による運営者の復旧は維持する。

## 検証

- 基点ソースの隔離コピーに対し、上記の認証・削除・アップロード・受信上限の20ケースがすべて失敗することを確認。巨大本文は16MiBで必ず終わる有限のテストデータとし、無制限送信は行わない。
- Node全585テスト（追加27）、Pythonの公開版検証8テストが成功。追加した競合・移行・世代別復旧の32テストも単独で成功。
- 既存の保管庫・運営・R2移動・復旧テスト53件、CI登録・DOM挿入・SHA固定・テスト分割・配信用minifyの静的検査も成功。
- 実ブラウザ検査 `tools/check_audit_regressions.cjs` に、一般運営者が開発者のコード・再設定ボタンを見られず、通常プレイヤーの復旧操作は使える確認を追加。既存の切断時のスピン・ガチャ再送、古い認証応答、ログイン入力の検査も維持。
- 必須CIの `tools/check_vault_snapshot_worker.cjs` を拡張。実workerd・ローカルR2で、運営者の認証情報分離、raw/JSON共通の条件付き書込み、同一再送・異なる内容の拒否、再開・完成後の上書き拒否、世代付きファイルの削除後復旧を実行する。

このローカル環境ではWranglerが `uv_interface_addresses` の取得に失敗して起動できないため、実workerd検査の完了はGitHub CIで必須確認する。公開環境のネットワーク設定・ヘッダー・制限を変更して回避することはしない。実際の不正利用の有無や、既に破損した本番ファイルの有無を、この使い捨て環境の検査だけで判断することはできない。

R2の条件付き作成は、[Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) と [条件付き書込みの整合性](https://developers.cloudflare.com/r2/reference/consistency/#conditional-writes) の仕様に基づく。
