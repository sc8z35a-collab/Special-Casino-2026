# 運営の画面を見る機能（状態転送方式）の設計

運営サイトのプレイヤー一覧の「見る」で、オンラインのプレイヤーのゲーム画面をリアルタイムで見る機能です。
実装: `server/core/opswatch.js` / `js/net/watchcrypto.js` / `js/net/watchfeed.js` / `ops/watch.js`。
使い方と指定との対応表は README の「運営の画面を見る機能」。ここは作った人向けの仕組みの説明です。

## なぜ映像ではなく状態か

依頼は「H.264・300kbps・低遅延で映像を送る。ただしゲームの状態だけを送って再現するほうが安く済むならそちら」でした。状態転送にしました。

- ブラウザが映像にできるのは canvas 1 枚（`captureStream`）か、本人の許可の表示が出る画面共有だけ。ゲームはスロットの canvas のほかにメニュー・チャット・クエストなど大半が DOM と 3D で、映像にすると肝心の部分が写りません。許可の表示なしに端末の画面を撮る手段もありません（あってはいけません）。
- 映像は 300kbps で 1 時間約 135MB。状態は 1 フレーム約 260 バイトで、変わったときだけ送ります。実測（本物のゲームを 540P・20fps で見ながらスピン）は平均 0.3 KB/秒（約 2.5kbps）。
- Cloudflare の Durable Object には映像の符号化も復号もできません（状態なら中継するだけ）。
- 3D の画面は「どの画面か」を送るだけで済み、特別扱いが要りません。

映像が必要になったときの道: ゲームの canvas を `WebCodecs` の `VideoEncoder`（H.264・300kbps 固定）で符号化して同じ封をした経路に流す。ただし DOM の画面は写らないので、状態転送とは目的が違います。

## 流れ

```
運営サイト                         サーバー (Durable Object)                 プレイヤーのゲーム
  │ ① 鍵ペアを作る (ECDH P-256)
  │── POST /api/ops/watch/start {player, quality, fps, pub} ──▶
  │                                 検査（運営者・オンライン・同時数・使用量…）
  │                                 ログ watch_start、ops_watch_log に行を作る
  │                                 ──── 'view' {sid, on, q, fps, pub} ───────────▶ ② 鍵ペアを作り、
  │                                 ◀──── POST /api/watch/hello {sid, pub} ────────    共有鍵を作る
  │◀── 'watchhello' {sid, pub, e} ──  （e: 鍵の世代。hello のたびに +1）
  │ ③ 共有鍵を作る
  │                                 ◀── 'view' frame {sid, e, n, d} ───（WebSocket、
  │◀── 'watchframe' {sid, e, n, d} ──   Node では POST /api/watch/frame）
  │ ④ 開いて sane() → 描く          大きさ・300kbps・カウンターを検査して中継
  │◀── 'watchstat' 1 秒ごと ─────────  （通信量はサーバーの数え）
  │── POST …/quality / …/stop / …/message ──▶                                  
  │                                 終了: ログ watch_end（強制なら watch_force_end）
  │◀── 'watchend' {reason} ──────── ──── 'view' {on:false} ───────────────────▶ 送るのをやめる
```

- 共有鍵 = HKDF-SHA256(ECDH, salt = 監視の ID, info = `two-state watch v1|運営の公開鍵|プレイヤーの公開鍵`)。AES-256-GCM、IV = 鍵の世代(4 バイト) + カウンター(8 バイト)、認証データ = `sid|e|n`。
- 接続だけが切れて戻ったときは、同じ鍵で続けます。ゲームのページが読み込み直されたときは、再接続の `hello` の応答（`view` フィールド）で同じ監視の再開を頼まれ、新しい鍵ペアで `hello` をやり直して鍵の世代を進めます。運営サイトのページが再読み込みされたときは鍵が失われるので、`sync()` が古い監視を止めます。
- `watchhello` の通知を取りこぼしたとき、運営サイトは `GET /api/ops/watch/state` に載っているプレイヤーの公開鍵（秘密ではない）で鍵を作り直します。開始の応答より先に届いたイベントは溜めておいて、応答のあとで処理します。

## 守っていること（そして試験で確認していること）

| 性質 | どう守るか | 確認 |
| --- | --- | --- |
| 押すまで何も送らない | `view` の合図はサーバーが `start` のあとにだけ送る | `opswatch.test.js`（合図なし）／実ブラウザ（開始前は送信なし） |
| 一方通行 | 運営からゲームへ届くのは `view`（開始・画質・停止）だけ。キー・タップ・命令にあたるメッセージは存在しない | `opswatch.test.js`（`view` のキー集合） |
| サーバーは中身を読めない | フレームは封をしたまま中継。サーバーが見るのは大きさ・カウンター・誰から誰へ | 同上（`ev.d` が暗号文で、数値が平文に現れない） |
| 再送・改ざん・流用ができない | カウンターは増加のみ、認証データに監視・世代・カウンター | 同上（再送・別人・壊した 1 文字・別カウンター・別の監視） |
| 300kbps を超えない | 1 回の監視ごとに毎秒 37,500 バイト（バースト 2 秒分）で、超えた分は捨てる | 同上（60 フレームの連打） |
| 30 分で終わる | `expiresAt`。フレームと 2 秒ごとの `tick` が見る | 同上（時計を進める） |
| 緊急時に全部止まる | 緊急停止・ロックダウンは `host.stop` の前に `terminateAll`。攻撃の気配（シールドの限界の半分）・運営権の剥奪・処分・使用量 100% は `tick` | 同上（ロックダウン・処分・運営権）、Discord の【危険】 |
| 本人に知らせない | ゲームは何も描かない | 実ブラウザで見ている間の表示要素を比較して差がない |
| 記録 | 開始・終了を改ざん検知つきの運営ログ（セキュリティ）と `ops_watch_log`。サーバーの再起動で途切れたものは次の起動で閉じる | 同上（再起動） |
| 届いたものを信じない | `ops/watch.js` の `sane()`：数値は範囲に丸め、文字は自前の表だけ | `opswatch.test.js`（悪意のあるフレーム） |
| 連打されない | プレイヤー 1 人あたり 30 フレーム/秒まで（それ以上は捨てる）、開始・画質・メッセージにも制限 | 同上 |

## 運用メモ

- 誰がいつ誰を見たか: 運営サイトの「ログ」→ 分類「セキュリティ」→ `watch_start` / `watch_end` / `watch_force_end`、または `GET /api/ops/watch/log`（運営者全員が読めます）。閲覧者（読み取り専用）はログの要約だけ読めます（詳細は出ません）。
- 使用量: サーバータブの「通信量の内訳」の「映像通信」に、運営の画面を見る機能と友達の観戦が入ります。月の使用量が 95% を超えると新しい監視は始められず、100% で進行中のものも終わります。
- Cloudflare: 監視の一覧はメモリだけ。Durable Object が入れ替わると全部終わり、次の起動で `ops_watch_log` に `restart` と書かれます（運営サイトは 3 秒〜10 秒おきの確認で気づいて「サーバー側で終了しました」と出します）。フレームを送っている間はオブジェクトは眠りません（`op: "view"` は「プレイヤーの操作」には数えません）。
- 友達の観戦（ゲーム内）は別の仕組みで、もともと状態だけを送っています。画質（720P / 460P）と 24fps は観戦する側の描画だけを変えます（`js/ui/watchquality.js`）。
